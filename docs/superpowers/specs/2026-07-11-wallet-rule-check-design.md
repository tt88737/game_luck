# 钱包规则体检与奖励启用约束设计

## 背景

当前 C 端奖励领取可能出现“钱包规则不存在”。根因不是玩家操作问题，而是 B 端活动奖励配置缺少对钱包规则依赖的显性提示和启用约束。

奖励发放实际依赖以下组合：

- 币种：例如 `GC`、`SC`、`RC`
- 来源类型：普通活动奖励为 `PROMOTION`，每日登录奖励为 `DAILY_REWARD`
- 钱包规则状态：启用
- 入账开关：允许入账
- 释放方式、流水要求、提现/兑换开关等后续资金规则

运营在配置活动奖励时只看到币种和金额，不知道还需要检查钱包规则，导致活动配置成功但玩家领取失败。

## 目标

在 B 端活动奖励配置阶段暴露钱包规则依赖，做到：

- 运营能看懂缺什么规则。
- 缺失或禁用的钱包规则不能让活动启用。
- 可以保存草稿，方便运营先配置活动内容。
- C 端不暴露后台技术词，玩家只看到可理解的不可领取提示。
- 后端仍保留强校验，避免绕过前端直接启用或领取。

## 不做范围

- 不把活动奖励和钱包规则合并成一个大模块。
- 不自动静默创建钱包规则。
- 不改变钱包账务核心规则、流水规则或现有钱包规则表结构。
- 不新增审批流。

## 推荐方案

采用“配置时实时体检 + 阻止启用”。

B 端活动奖励表单新增“钱包规则体检”区域：

- 每个奖励项显示一行检查结果。
- 检查维度为 `币种 + 来源类型`。
- 状态包括：
  - `可发放`：规则存在、启用、允许入账。
  - `规则不存在`：没有匹配的钱包规则。
  - `规则已停用`：规则存在但状态停用。
  - `禁止入账`：规则存在但入账开关关闭。
- 异常行提供“去创建/编辑钱包规则”入口。

启用约束：

- 新增或编辑活动时，可以保存为停用状态。
- 当保存为启用状态，或者从列表点击启用时，后端必须检查钱包规则。
- 检查不通过时，接口返回明确业务错误，不改变活动状态。

## 来源类型映射

活动类型到钱包来源类型由后端统一决定，前端只展示结果：

| 活动类型 | 钱包来源类型 |
| --- | --- |
| `DAILY_LOGIN` | `DAILY_REWARD` |
| 其他普通奖励 | `PROMOTION` |

后续新增活动类型时，只在一个后端映射方法里扩展，避免每个模块重复强调。

## 后端设计

新增活动奖励钱包规则检查能力：

- 输入：活动类型、奖励项列表、普通奖励币种和金额。
- 输出：每个币种对应的钱包规则检查结果。

检查逻辑：

1. 根据活动类型解析 `sourceType`。
2. 解析实际奖励项：
   - 每日登录奖励使用 `rewardItems`。
   - 普通奖励使用 `currencyCode + rewardAmount`。
3. 对每个奖励项调用钱包规则查询能力。
4. 返回规则是否存在、是否启用、是否允许入账。

强校验位置：

- 新增活动且状态为 `ACTIVE`。
- 编辑活动且状态为 `ACTIVE`。
- 列表启用活动。
- 奖励领取前继续沿用钱包核心校验，作为最后防线。

## B 端设计

页面：促销中心 / 促销奖励。

表单新增“钱包规则体检”区域，放在奖励配置下面、状态开关上方。

交互：

- 打开新增/编辑弹窗时自动检查。
- 修改活动类型、币种、奖励金额、奖励项时重新检查。
- 检查中显示加载态。
- 检查失败或网络异常时不允许启用，只允许保存停用状态。
- 如果状态选择启用但体检未通过，确认按钮旁提示“请先补齐钱包规则后再启用”。

列表：

- 可选增强：奖励列表增加“规则状态”标签。
- 当前阶段可先不加列表列，先保证表单和启用动作可靠。

文案：

- 面向运营使用“钱包规则”“允许入账”“规则已停用”。
- 不展示 `DAILY_REWARD`、`PROMOTION` 作为主文案，只在辅助信息或 tooltip 中展示。

## C 端设计

C 端不展示“钱包规则不存在”。

当领取失败原因是钱包规则缺失、停用或禁止入账时：

- 中文：`奖励暂不可领取，请稍后再试`
- 英文：`Reward is temporarily unavailable. Please try again later.`

后台日志和 B 端错误仍保留具体原因，方便运营修复。

## 验收标准

- B 端配置每日登录奖励 `GC 100 + SC 1` 时，能看到 `GC/DAILY_REWARD` 与 `SC/DAILY_REWARD` 的规则检查结果。
- 缺少任意奖励项的钱包规则时，活动不能启用。
- 钱包规则存在但停用时，活动不能启用。
- 钱包规则存在但禁止入账时，活动不能启用。
- 规则全部可用时，活动可以启用，C 端领取成功。
- 玩家领取失败时不再看到“钱包规则不存在”。
- 后端直接调用启用接口也会被规则体检拦截。
- 中文和英文文案均覆盖。

## 验证计划

- 后端单测：
  - 每日登录奖励缺少 SC 规则时启用失败。
  - 普通奖励缺少 PROMOTION 规则时启用失败。
  - 规则存在但禁止入账时启用失败。
  - 规则全部可用时启用成功。
- 前端检查：
  - `pnpm --dir admin-ui check:i18n`
  - `pnpm --dir admin-ui build:dev`
- H5 检查：
  - `npm --prefix h5 run build`
- 可用时运行后端 Maven 测试和打包。
