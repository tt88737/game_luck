# 钱包规则模板化与运营化配置设计

## 背景

当前钱包规则已经能控制 `币种 + 来源类型` 的入账、释放、提现、兑换和流水要求，但 B 端页面仍然偏技术配置。运营看到的是 `GAME_PROFIT`、`MANUAL_REVIEW`、`允许入账`、`需要业务流水` 等字段，难以判断应该怎么配置。

实际使用中还暴露出三个问题：

- 默认规则不完整时，活动、每日奖励、人工调整等业务会在使用阶段失败。
- 来源类型存在别名或重复表达，例如 `GAME_PAYOUT` 与 `GAME_PROFIT` 都显示为“游戏派奖”，`ADJUST`、`ADJUSTMENT`、`MANUAL_ADJUST` 都接近“人工调账”。
- 人工调整不是固定一种资金策略，有时需要打码，有时不需要打码，应该由本次操作决定，而不是被一条固定钱包规则锁死。

上一阶段的“钱包规则体检”解决了活动启用前发现缺失规则的问题。本阶段要进一步把钱包规则做成可维护的系统底座：系统默认生成基础规则，B 端只暴露运营能理解的配置项，技术枚举在底层收口。

## 目标

- 系统提供默认钱包规则模板，初始化或补齐时自动生成常用规则。
- 已有租户可以一键补齐默认规则，不覆盖人工修改过的自定义规则。
- B 端来源类型下拉只展示主来源，隐藏重复、过时或内部别名。
- 钱包规则页面从“技术字段表单”升级为“业务策略配置”。
- 人工调整支持本次操作选择资金策略：无需流水、需要流水、人工审核。
- 中英文文案统一，后续模块不再重复解释枚举含义。

## 不做范围

- 不重写历史钱包流水的 `source_type`。
- 不删除数据库中已有的旧枚举值，避免影响历史查询和报表。
- 不引入通用规则引擎、表达式引擎或复杂审批流。
- 不把所有业务模块的资金规则硬编码到前端。
- 不改变钱包账务幂等、余额计算、流水记录、释放记录的核心逻辑。

## 方案对比

| 方案 | 内容 | 优点 | 风险 | 结论 |
| --- | --- | --- | --- | --- |
| A. 只改页面文案 | 把字段翻译成中文，来源下拉去重 | 快 | 默认规则仍要人工配置，后续还会漏 | 不推荐 |
| B. 默认模板 + 来源收口 + 表单运营化 | 后端维护模板，B 端补齐规则，页面按业务分组展示 | 覆盖当前痛点，改动可控 | 需要补一个服务层能力和迁移脚本 | 推荐 |
| C. 完整策略中心 | 把所有钱包规则抽象成策略、版本、审批、灰度 | 扩展性最强 | 当前阶段过重，会拖慢底座搭建 | 暂缓 |

本阶段采用方案 B。

## 来源类型收口

来源类型分两层管理：

- 标准来源：新业务、新规则、新下拉默认只使用这些值。
- 历史别名：保留识别和显示能力，但不再作为新增配置选项。

| 标准来源 | 运营显示 | 用途 | 历史别名处理 |
| --- | --- | --- | --- |
| `REGISTER_BONUS` | 注册赠送 | 注册奖励入账 | 保留 |
| `DAILY_REWARD` | 每日奖励 | 每日登录、日常奖励入账 | 保留 |
| `TASK_REWARD` | 任务奖励 | 任务类奖励入账 | 保留 |
| `DEPOSIT` | 充值 | RC 充值入账 | 保留 |
| `GAME_BET` | 游戏投注 | 投注扣账、冻结、结算 | 保留 |
| `GAME_PROFIT` | 游戏派奖 | 游戏盈利、派奖入账 | `GAME_PAYOUT` 只做历史别名 |
| `GAME_REFUND` | 游戏退款 | 注单取消、退款 | 保留 |
| `REDEMPTION` | 兑换 | 兑换扣减、审核 | 保留 |
| `PROMOTION` | 活动奖励 | 通用活动奖励入账 | 保留 |
| `MANUAL_ADJUST` | 人工调账 | 后台人工加减款 | `ADJUST`、`ADJUSTMENT` 只做历史别名 |
| `TURNOVER` | 流水调整 | 流水累计或修正 | 仅在流水相关页面展示 |

页面规则：

- 钱包规则新增/编辑下拉只展示标准来源。
- 流水、账变、释放等历史查询页面可以显示历史别名，但文案后追加“历史来源”标识。
- 如果历史数据中出现 `GAME_PAYOUT`，显示为“游戏派奖（历史来源）”。
- 如果历史数据中出现 `ADJUST` 或 `ADJUSTMENT`，显示为“人工调账（历史来源）”。

## 默认规则模板

系统维护一份默认模板清单。模板用于：

- 新环境初始化 SQL。
- 已有租户一键补齐缺失规则。
- 钱包规则页面展示“系统推荐配置”。
- 活动奖励体检失败时引导补齐。

默认模板以 `tenant_id + currency_code + source_type` 为唯一键。补齐时只插入不存在的组合；如果规则已存在，不覆盖状态、释放方式、提现能力、兑换能力、流水要求和备注。

建议默认模板：

| 币种 | 来源 | 运营含义 | 入账 | 提现 | 兑换 | 到账策略 | 默认流水 | 备注 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| GC | `REGISTER_BONUS` | 注册送 GC | 允许 | 否 | 否 | 立即到账 | 0 | 体验金，不可提现兑换 |
| SC | `REGISTER_BONUS` | 注册送 SC | 允许 | 否 | 否 | 立即到账 | 0 | 默认不直接兑换，后续可按风控调整 |
| GC | `DAILY_REWARD` | 每日 GC 奖励 | 允许 | 否 | 否 | 立即到账 | 0 | 小额运营奖励 |
| SC | `DAILY_REWARD` | 每日 SC 奖励 | 允许 | 否 | 否 | 立即到账 | 0 | 当前阶段按已确认的每日奖励配置落地 |
| SC | `PROMOTION` | 活动 SC 奖励 | 允许 | 否 | 否 | 满足流水后释放 | 0 | 活动可传入实际流水要求 |
| GC | `PROMOTION` | 活动 GC 奖励 | 允许 | 否 | 否 | 立即到账 | 0 | 活动赠送 GC |
| RC | `DEPOSIT` | 充值入账 | 允许 | 是 | 否 | 立即到账 | 0 | 充值资金 |
| SC | `GAME_PROFIT` | 游戏派奖 SC | 允许 | 否 | 是 | 满足流水后释放 | 0 | 游戏盈利后可兑换 |
| GC | `GAME_PROFIT` | 游戏派奖 GC | 允许 | 否 | 否 | 不释放 | 0 | GC 不进入可兑资金 |
| SC | `GAME_REFUND` | 游戏退款 SC | 允许 | 否 | 是 | 立即到账 | 0 | 退款不新增打码要求 |

| SC | `MANUAL_ADJUST` | 人工调账 SC | 允许 | 否 | 可配置 | 默认人工审核 | 0 | 具体是否打码由本次操作决定 |
| GC | `MANUAL_ADJUST` | 人工调账 GC | 允许 | 否 | 否 | 立即到账 | 0 | 后台补发或修正 GC |

## 补齐规则机制

B 端钱包规则页面增加“补齐默认规则”能力。

流程：

1. 后端读取当前租户已存在的钱包规则。
2. 与系统默认模板按 `tenant_id + currency_code + source_type` 对比。
3. 返回缺失清单和已存在清单。
4. 运营点击确认后，只插入缺失项。
5. 记录操作日志，包含插入数量、租户、操作人、模板版本。

约束：

- 补齐默认规则不修改已有规则。
- 如果默认模板升级，新增模板项可以再次补齐。
- 如果某条历史规则被运营停用，补齐动作不能重新启用它。
- 补齐接口需要后台权限，例如 `wallet:rule:seed`。

## B 端页面设计

钱包规则列表保留表格，但展示内容改为运营可读：

- 币种
- 来源
- 资金用途
- 到账策略
- 流水要求
- 是否可提现
- 是否可兑换
- 状态
- 是否系统默认
- 操作

新增/编辑弹窗按业务分组：

### 1. 基础信息

- 币种
- 来源
- 规则名称
- 状态

来源下拉使用标准来源，不展示历史别名。

### 2. 资金方向

用业务文案替代技术开关：

| 字段 | 运营文案 |
| --- | --- |
| `creditEnabled` | 是否允许给会员增加余额 |
| `debitEnabled` | 是否允许从会员余额扣减 |

### 3. 资金用途

| 字段 | 运营文案 |
| --- | --- |
| `withdrawEnabled` | 这笔资金是否可提现 |
| `exchangeEnabled` | 这笔资金是否可兑换 |

页面需要补充短提示：

- 可提现：用于 RC 等现金类资金。
- 可兑换：用于 SC 达标后兑换 RC。
- GC 通常不可提现、不可兑换。

### 4. 到账策略

| 技术值 | 运营文案 | 说明 |
| --- | --- | --- |
| `IMMEDIATE` | 立即到账 | 发放后马上可用 |
| `AFTER_TURNOVER` | 完成流水后可用 | 达到流水要求后释放 |
| `NEVER` | 仅记录，不释放 | 适合只做游戏内余额或不可释放资金 |
| `MANUAL_REVIEW` | 人工审核后处理 | 需要后台人工确认 |

### 5. 流水要求

现有 `turnoverRequired` 和 `defaultRequiredTurnover` 容易误解，页面统一解释为：

- 是否要求业务提供流水：活动、游戏、人工调整是否需要传入本次实际流水要求。
- 默认流水要求：当业务没有传入流水时使用的兜底值。

页面显示推荐提示：

- 活动奖励：建议由活动配置传入流水。
- 游戏派奖：建议由游戏结算传入流水。
- 人工调账：建议在本次调账操作里选择。

## 人工调账策略

人工调账不能只靠一条固定规则决定是否打码。本阶段设计为“钱包规则给默认值，调账操作可覆盖”。

覆盖边界：

- 只有 `MANUAL_ADJUST` 来源允许在本次操作覆盖到账策略和流水要求。
- 活动奖励、每日奖励、游戏派奖、充值等业务仍按各自业务配置和钱包规则执行，不能在通用钱包入账接口随意覆盖。
- 覆盖后的策略必须写入账变、释放记录和操作日志，保证后续查询、对账和审计能还原当时的决定。

人工调账页面需要新增资金策略选择：

| 策略 | 行为 |
| --- | --- |
| 无流水，立即到账 | `releaseMode = IMMEDIATE`，`requiredTurnover = 0` |
| 需要流水 | `releaseMode = AFTER_TURNOVER`，操作人填写流水金额或流水倍数计算结果 |
| 人工审核 | `releaseMode = MANUAL_REVIEW`，进入待审核释放状态 |

后端校验：

- 操作传入的 `releaseMode` 必须在该来源允许范围内。
- 如果选择“需要流水”，流水值必须大于 0，实际业务可按金额倍数计算后传入。
- 如果不传策略，则使用 `MANUAL_ADJUST` 钱包规则默认策略。

审计日志必须记录：

- 操作人
- 调账币种
- 调账金额
- 调账原因
- 本次资金策略
- 本次流水要求

## 字典与国际化

后续不应每个模块重复写来源、状态、释放模式文案。

统一策略：

- 数据库字典维护标准枚举和是否默认展示。
- 前端 `businessLabels` 作为兜底映射和历史别名兼容层。
- 后端错误与日志使用 i18n key，避免直接抛英文枚举。
- 中英文必须同时补齐。

字典建议新增或调整字段：

| 字典类型 | 用途 |
| --- | --- |
| `gl_wallet_biz_type` | 钱包来源标准值与历史别名 |
| `gl_wallet_release_mode` | 到账策略 |
| `gl_wallet_rule_template_status` | 系统默认、自定义、历史 |

历史别名在字典中可标记为 `is_default = N` 或后续扩展 `visible_in_form = N`。如果当前字典结构暂不支持 `visible_in_form`，前端先用白名单过滤标准来源，数据库字典作为下一步优化。

## 后端设计

新增服务能力：

- `listDefaultTemplates()`：返回系统默认规则模板。
- `previewMissingDefaultRules(tenantId)`：预览缺失规则。
- `seedMissingDefaultRules(tenantId)`：补齐缺失规则。
- `canonicalSourceType(sourceType)`：把历史别名映射为标准来源，仅用于展示、查询归并或新业务入参规范化。

补齐接口建议：

- `GET /wallet/rule/default/preview`
- `POST /wallet/rule/default/seed`

返回结构建议：

| 字段 | 含义 |
| --- | --- |
| `currencyCode` | 币种 |
| `sourceType` | 标准来源 |
| `sourceLabel` | 运营展示文案 |
| `exists` | 当前租户是否已有规则 |
| `willCreate` | 本次是否会创建 |
| `recommendedReleaseMode` | 推荐到账策略 |
| `recommendedTurnover` | 推荐默认流水 |
| `remark` | 运营说明 |

## 数据迁移策略

本阶段不迁移历史流水，只做规则补齐和新增配置收口。

需要处理：

- 初始化 SQL 增加完整默认模板。
- 已部署环境提供补齐接口或一次性 SQL。
- 字典中新增标准来源 `GAME_PROFIT`、`MANUAL_ADJUST` 时，旧值保留。
- 前端新增配置过滤标准来源，历史查询仍能显示旧值。

## 验收标准

- 钱包规则页面能看到“补齐默认规则”入口。
- 点击预览能列出缺失的默认规则，不直接写库。
- 确认补齐后，只新增缺失规则，不覆盖已有规则。
- 来源下拉不再出现重复“游戏派奖”和重复“人工调账”。
- 历史流水中的旧来源仍能正常显示和查询。
- 钱包规则表单不再直接暴露难懂技术词，字段按业务分组展示。
- 人工调账可以在本次操作选择是否需要流水。
- 中英文文案完整，中文运营可理解，英文不暴露后端枚举作为主文案。
- 后端直接调用补齐接口、钱包规则新增接口、活动启用接口时都有权限和参数校验。

## 测试重点

- 默认模板预览：缺失、部分存在、全部存在三种情况。
- 补齐默认规则：幂等调用两次不会重复插入。
- 已停用规则：补齐动作不重新启用。
- 来源下拉：新增/编辑只展示标准来源。
- 历史账变：`GAME_PAYOUT`、`ADJUSTMENT` 仍能显示为可读文案。
- 人工调账：三种资金策略分别生成正确释放方式和流水要求。
- 活动奖励体检：补齐默认规则后能通过对应币种和来源检查。

## 实施顺序

1. 后端默认模板与补齐接口。
2. SQL 默认模板补全。
3. 前端来源标准化与历史别名显示。
4. 钱包规则页面运营化改版。
5. 人工调账本次资金策略。
6. 中英文 i18n 与回归验证。
