# Member ID And System ID Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make `member_no` the short, user-facing Member ID (`GL000001` and auto-expanding digits), keep `id/member_id` as System ID, migrate existing member numbers, and unify B-side/C-side wording and search behavior.

**Architecture:** Keep database relationship semantics stable: `gl_member_profile.id` and all business-table `member_id` columns remain internal System ID references. `gl_member_profile.member_no` remains the physical field, but becomes the official user-facing Member ID generated by one backend service and displayed as `会员ID`. A guarded SQL migration normalizes old demo/Snowflake-style values without touching wallet/order/ledger foreign keys.

**Tech Stack:** Java 17, Spring Boot, MyBatis Plus, MySQL, Vue 3, Vite, Element Plus, existing GameLuck i18n.

## Product Rules

- `系统ID`: `gl_member_profile.id` and all business-table `member_id` foreign keys.
- `会员ID`: `gl_member_profile.member_no`.
- `会员ID` format: `GL` + numeric sequence, minimum 6 digits.
- Auto-expansion examples:
  - `1` -> `GL000001`
  - `482913` -> `GL482913`
  - `1000000` -> `GL1000000`
  - `10000000` -> `GL10000000`
- Do not rename the physical database column `member_no`.
- Do not change wallet/order/ledger table foreign keys.
- B-side and C-side visible copy must not use `会员编号`.

- [ ] **Step 3: Create generator**

Create `MemberIdGenerator.java`:

```java
package com.gameluck.member.service;

import cn.hutool.core.util.IdUtil;
import org.springframework.stereotype.Component;

@Component
public class MemberIdGenerator {

    private static final String PREFIX = "GL";
    private static final int MIN_DIGITS = 6;

    public String next() {
        long numeric = Math.abs(IdUtil.getSnowflakeNextId() % 1_000_000_000L);
        if (numeric == 0) {
            numeric = IdUtil.getSnowflakeNextId() % 1_000_000L;
            if (numeric <= 0) {
                numeric = 1;
            }
        }
        return format(numeric);
    }

    public String format(long numeric) {
        if (numeric < 0) {
            throw new IllegalArgumentException("Member ID numeric value must not be negative");
        }
        String value = Long.toString(numeric);
        if (value.length() < MIN_DIGITS) {
            value = "0".repeat(MIN_DIGITS - value.length()) + value;
        }
        return PREFIX + value;
    }
}
```

Note: this first implementation preserves current no-new-table behavior for a small slice. It uses existing Snowflake entropy but exposes a short `GL` number. A later high-volume hardening slice can replace `next()` with a DB sequence table without changing callers.

- [ ] **Step 1: Add migration SQL**

Create `backend/script/sql/gameluck_member_public_id.sql`:

```sql
-- Normalize public member IDs. Internal ids and business-table member_id foreign keys are not changed.

SELECT tenant_id, member_no, COUNT(*) AS duplicate_count
FROM gl_member_profile
WHERE del_flag = '0'
GROUP BY tenant_id, member_no
HAVING COUNT(*) > 1;

UPDATE gl_member_profile
SET member_no = CONCAT('GL', LPAD(CAST(id AS CHAR), 6, '0')),
    update_time = NOW()
WHERE del_flag = '0'
  AND (
    member_no IS NULL
    OR member_no = ''
    OR member_no REGEXP '^M[0-9]+$'
    OR member_no REGEXP '^MB-SEED-[0-9]+$'
    OR member_no REGEXP '^MB[0-9]{10,}$'
  );

SELECT tenant_id, member_no, COUNT(*) AS duplicate_count
FROM gl_member_profile
WHERE del_flag = '0'
GROUP BY tenant_id, member_no
HAVING COUNT(*) > 1;
```

Rationale: `GL + id` is deterministic, collision-free under current primary-key uniqueness, auto-expands beyond 6 digits, and does not alter wallet/order foreign keys.
