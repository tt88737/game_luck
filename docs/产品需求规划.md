# TangLuck 产品需求规划

## 1. 文档定位

本文是 TangLuck 项目的项目级产品需求规划，用于统一产品目标、阶段边界、模块职责、关键状态机和验收口径。

本文不是单个模块的技术设计，也不是美国法律意见。涉及 Sweepstakes 合规、开放州、SC 发放、AMOE、支付商准入、App 上架等事项，最终仍需由业务、美国律师、支付商和平台审核团队确认。

## 3. 当前结论

TangLuck 按 **Sweepstakes Social Casino** 建设。当前第一验收目标不是一次性上线完整合规生产版本，而是先完成一个 **可演示的产品闭环**。

关键约束是：虽然第一阶段用于演示和联调，但底层接口、状态机、钱包账本和数据结构必须按 **合规 MVP** 的方向设计，避免后续上线合规能力时推倒重来。

## 5. 产品目标

### 5.1 P0 目标

P0 的目标是证明以下链路可以在当前 `luck-cloud` 仓库内真实跑通：

1. 用户注册/登录。
2. 注册后异步获得注册赠送。
3. 服务端创建并维护 GC/SC 钱包。
4. 用户进入大厅并启动游戏。
5. 游戏供应商回调真实改 GC/SC 钱包。
6. 用户进入商店并创建充值订单。
7. 后台模拟充值成功后 pay 通知 wallet 发放 GC + bonus SC。
8. 用户提交兑换申请。
9. 后台审核兑换，模拟打款成功或拒绝。
10. wallet 完成 SC 冻结、扣减或解冻。
11. 后台 BI 能看到注册、钱包、游戏、充值、兑换、活动和风控闭环指标。

### 5.2 长期目标

长期目标是形成可运营、可审计、可合规上线的 Sweepstakes Social Casino：

- 会员端完整支持商店、兑换、大厅、奖励、我的。
- 后台完整支持用户、钱包、活动、游戏、充值、兑换、KYC、风控、BI、客服。
- GC/SC 全链路账实一致、可审计、可追溯。
- 地区准入、KYC、风控、AMOE、No Purchase Necessary 和用户告知形成合规闭环。
- 活动体系支持运营配置、预算、规则版本、法务审批、领取记录和发放记录。

## 7. 关键硬边界

### 7.1 wallet 与 pay

`luck-module-wallet` 是 GC/SC 余额唯一真相来源。任何 GC/SC 余额变化都只能通过 wallet 的统一账变服务发生。

`luck-module-pay` 不能直接改 wallet 表。pay 在充值成功后只能调用 wallet 发放 GC + bonus SC；在提款/打款成功后只能通知 wallet 完成冻结 SC 扣减。

### 7.2 member 与 active

member 只负责注册成功并发布用户创建事件。注册赠送由 active 消费注册事件后异步执行。

注册赠送失败不能回滚注册。active 必须保证同一用户同一注册赠送活动只发放一次，并能记录处理状态、失败原因和补偿入口。

### 7.3 game 与 wallet

游戏改账以现有供应商回调链路为准：

- App 进入游戏：`POST /app-api/game/into-game`
- App 查询会话：`POST /app-api/game/query`
- App 关闭会话：`POST /app-api/game/close`
- 供应商回调：`POST /game/notify/{platformCode}/{callbackScene}`

game 负责解析供应商回调、幂等、订单和结算语义，再调用 wallet 完成 GC/SC 扣减、派彩和 SC 打码变化。

### 7.4 mobile 与 admin

mobile 只做会员端。以下能力不得出现在 mobile：

- 模拟充值成功。
- 人工发币。
- 兑换审核。
- KYC 人工通过。
- 活动配置。
- 风控规则配置。
- 任意管理端 CRUD。

这些能力放在 admin、后端测试脚本或受控后台接口中。

## 8. P0 产品闭环

### 8.1 注册与注册赠送

流程：

1. 用户提交邮箱注册。
2. member 校验邮箱、密码、生日、国家、州、设备、注册来源和条款确认。
3. 注册地区和年龄不满足时直接失败。
4. 注册成功后创建用户并发布 `MemberUserCreateMessage`。
5. wallet 初始化用户 GC/SC 钱包。
6. active 消费注册事件并执行注册赠送。
7. active 调用 wallet 发放 GC + SC。
8. mobile 首页刷新钱包余额。

验收：

- 注册成功不依赖 active 发奖成功。
- 注册赠送失败可重试或后台补偿。
- 注册赠送有发放记录和钱包流水。
- 同一用户同一注册赠送活动不可重复发放。

### 8.2 钱包与账本

P0 钱包必须是真实账本：

- GC 余额。
- SC 未使用余额。
- SC 可兑余额。
- SC 冻结余额。
- SC 总打码量。
- SC 已完成打码量。
- GC/SC 账变流水。
- SC 打码流水。
- 会话账变汇总。

App 只读钱包，不直接改账。P0 需要提供会员端钱包查询接口，用于 mobile Header 和兑换页展示。

### 8.3 大厅与游戏

流程：

1. mobile 展示大厅机台、最近、收藏和 GC/SC 切换。
2. 用户选择游戏和钱包类型。
3. game 创建或查询游戏会话。
4. 供应商回调进入 `GameCallbackController`。
5. game 完成幂等和结算。
6. game 调用 wallet 修改 GC/SC 余额与打码量。
7. mobile 退出游戏后刷新钱包。

验收：

- GC 投注/派彩真实改钱包。
- SC 投注/派彩真实改钱包。
- SC 打码量正确变化。
- 重复回调不重复改账。
- 回调失败可查询和补偿。

### 8.4 商店与充值

P0 允许后台模拟充值成功，但账变路径必须等同真实支付回调。

流程：

1. mobile 读取充值包。
2. 用户创建充值订单。
3. admin 执行模拟支付成功。
4. pay 将充值订单置为成功。
5. pay 调用 wallet 发放 GC + bonus SC。
6. mobile 刷新钱包余额。

验收：

- 前端不能直接加余额。
- pay 不能直接改 wallet 表。
- 重复模拟/回调不重复发放。
- 订单、发放、钱包流水可关联。
- 商店文案只能表达购买 GC，不能表达购买 SC。

### 8.5 兑换

P0 至少做到冻结和后台审核，真实打款可模拟。

流程：

1. mobile 展示 SC 可兑余额、冻结余额和打码进度。
2. 用户提交兑换申请。
3. 后端校验 KYC、地区、风控、余额、最低兑换额。
4. wallet 将 SC 可兑余额冻结。
5. admin 审核兑换。
6. 审核通过后 pay 执行模拟打款成功。
7. wallet 确认扣减冻结 SC。
8. 审核拒绝或打款失败时 wallet 解冻 SC。

验收：

- 未冻结 SC 不得创建有效兑换单。
- KYC 未通过不得兑换。
- 禁止州不得兑换。
- SC 可兑余额不足不得兑换。
- 审核通过、拒绝、失败都有状态和流水。

### 8.6 KYC 与地区准入

P0 不接真实 KYC 供应商，但必须有状态 Gate：

- 注册必须检查国家/州和年龄。
- 用户条款确认必须版本化记录。
- 兑换前必须检查 KYC 状态。
- KYC 状态至少包含：`NOT_SUBMITTED`、`PENDING`、`PASSED`、`REJECTED`。
- P0 可由 admin 手动设置 KYC 状态。

后续 M5 接入真实 KYC、地理定位和完整合规校验。

### 8.7 风控

P0 风控按 `风控模块设计方案.md` 执行，不在业务模块里散写规则。

第一阶段建立 `luck-module-risk`：

- `luck-module-risk-api`
- `luck-module-risk-server`
- `RiskApi.decision`
- `MEMBER_LOGIN`
- `MEMBER_LOGIN_FAIL`
- `MEMBER_REGISTER`
- `MEMBER_GUEST`
- `PASS / CHALLENGE / REVIEW / BLOCK`
- MySQL 决策摘要。
- 风控事件留痕。
- kill-switch 和 failure strategy。

认证切片先落地登录防爆破、注册防批量、游客注册防护。充值、兑换、活动领奖等高敏场景按同一 RiskApi 模型扩展。

## 13. 合规基线

P0 即使是演示闭环，也必须遵守以下基线：

- 不能卖 SC。
- 商店只能表达购买 GC 商品包。
- SC bonus 只能作为受规则控制的赠品或免费路径奖励。
- No Purchase Necessary / AMOE / Official Rules / Privacy / Responsible Gaming 在关键路径可达。
- 禁止州用户不能领取 SC、进入 SC Game 或兑换。
- 未通过 KYC 的用户不能兑换。
- 拒绝定位或位置不明时，高风险功能必须阻断或进入审核。
- 所有 GC/SC 变更必须可追溯。
- 所有兑换、KYC、风控、后台人工操作必须可审计。

## 15. P0 验收清单

### 15.1 会员端

- 用户可以注册、登录。
- 用户注册时完成国家/州、生日、设备、来源、条款确认。
- 用户注册后能进入大厅。
- Header 展示头像、VIP、GC/SC 余额。
- 用户能打开商店、兑换、大厅、奖励、我的。
- 用户能进入游戏并返回。
- 游戏回调后余额刷新。
- 用户能创建充值订单。
- 用户能提交兑换申请并看到审核状态。

### 15.2 后台

- admin 能查询用户、钱包、游戏回调、充值订单、兑换单。
- admin 能模拟充值支付成功。
- admin 能审核兑换。
- admin 能手动设置 KYC 状态。
- admin 能查看注册赠送发放结果。
- admin 有活动配置中心框架。
- admin 有风控配置/命中记录最小能力。
- admin 有 P0 BI 闭环看板。

### 15.3 账本

- 注册赠送写入 wallet 流水。
- 游戏投注/派彩写入 wallet 流水。
- 模拟充值成功写入 wallet 流水。
- 兑换冻结、扣减、解冻写入 wallet 流水。
- 重复事件不重复改账。

### 15.4 合规

- 年龄不满足不能注册。
- 禁止州不能注册或不能进入高风险功能。
- KYC 未通过不能兑换。
- 商店没有购买 SC 文案。
- No Purchase Necessary / AMOE / Official Rules 入口可见。
- 风控 BLOCK 时业务动作被阻断或进入审核。

## 18. 后续工作方式

后续任务拆分按 vertical slice 进行。每个 issue 尽量覆盖一条可验收业务链路，包括数据、接口、服务、前端、测试和验收。

优先级顺序：

1. 确认 P0 演示路径和测试账号。
2. 补齐 wallet 对外 API 与 App 查询接口。
3. 跑通注册事件到 active 发放。
4. 跑通 game 回调改账验收脚本。
5. 跑通 pay 模拟充值成功到 wallet 发放。
6. 跑通 redeem 冻结、审核、模拟打款。
7. 建立 risk 认证切片。
8. 建立 BI P0 看板。
9. mobile 五 Tab 对接真实 App API。
10. admin 补齐闭环支撑能力。
